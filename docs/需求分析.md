# 需求分析与设计

> 对 `docs/题目.md` 的分析、难点拆解与实现方案。本文同时是前后端与 Mock 服务之间的接口契约。

## 1. 范围与优先级

| 组 | 内容 | 本次实现 |
|---|---|---|
| A0–A5 | 基础、账号状态机、网关接入、建群、时间线与推送、Agent 接入 | 全部 |
| A6 | 前端页面 1–3 | 全部 |
| B1–B4 | 定时序列、群生命周期、登录会话、断线补齐 + run 详情页 | 全部 |
| C1 | 媒体下载与清理 | 实现 |
| C2 | 真实 LLM Agent | 视时间 |
| C3 | Playwright E2E | 视时间 |

**总则「任意时刻重启前后都成立」** 是全局约束：所有定时器、队列、游标、进度都必须落库，内存里只放可以随时丢弃的缓存。

## 2. 难点拆解与处理方案

### 2.1 事件流（at-least-once、≤1s 乱序、补投、断线）

- **收件箱（inbox）**：每个 SSE 事件先按 `eventId` 主键写入 `gateway_inbox`（`ON CONFLICT DO NOTHING` 天然去重 S2），原文存 `text`（不用 `jsonb`，避免 `\u0000` 之类内容写不进去导致丢失），再逐条在独立事务里处理。
- **游标**：重连 `since` 取「最后收到时刻往前 2 秒之前收到的最大 eventId」，即回退一个大于乱序窗口的时间段，保证乱序中尚未到达的小 eventId 会被重新拉到；重复的由主键去重。首次启动 `since=0` 拉全部历史。
- **处理失败**：处理逻辑在 `SAVEPOINT` 内执行；失败则回滚到保存点、把该行标 `failed`（记录错误、指数退避重试）、同事务写 `inconsistency` 推送事件，然后继续处理后续事件。连 inbox 都写不进时，原文追加写到本地 `data/inbox-spool.jsonl`，内存直接广播 `inconsistency`，后台定期回灌。
- **乱序敏感点只有成员进出**：`group_members` 保留墓碑行与 `last_event_id`，只应用比已记录更新的事件；本地合成的成员变更（建群写入群主、`ALREADY_MEMBER`、终态移除、退群确认）把 `last_event_id` 设为当时 inbox 的最大 eventId。
- **补投**：`message` 按 `(groupId, msgId)` 唯一去重；时间线按 `sentAt` 排序，所以补投的旧消息自然落在正确位置。

### 2.2 出站消息（不丢、不重、504、限流）

- **先落库再发送**：`POST send` 先插入 `queued` 行（`clientMsgId` 由我们生成 UUID），后台发送器再发。发送前同一事务里写 `in_flight_at` 与 `attempt_count`，所以「网关发出了数据库却没记录」不会发生。
- **同一出站记录不对应多条网关消息**：网关不按 `clientMsgId` 去重，所以只有在确认没发出后才重发：
  - 504 / 网络错误 / 请求超时 → `unknown`，`unknown_since = now`；
  - 解析器每 300ms 查 `by-client-id`：`200` → `sent`；`404` 且距 `unknown_since` ≥ 2s → 确认未发出 → 未重发过则回到 `queued` 并标 `resend_used`，发送器立即用同一 `clientMsgId` 重发；已重发过 → `failed (NETWORK_TIMEOUT)`；`503` → 保持 `unknown`，恢复后下一次轮询（≤300ms）即判定。
  - 崩溃时正处于 in-flight 的行：`in_flight_at` 超过发送超时 + 1s 仍未结案，按 `unknown` 处理（同样走查询，不盲目重发）。
- **受理与发出（S1）**：202 → `accepted`；`message_sent` → `sent`。所有状态更新都是条件更新（`WHERE delivery_status IN (...)`），`message_sent` 早于 202 响应到达也不会被覆盖回 `accepted`。
- **自己的消息回流（S3）**：`isOwn` = 发送者 `platformUserId` 属于我们的服务账号。若 `message` 事件先于 `message_sent` 到达，会先产生一行孤儿；`message_sent` 到达时在同一事务里删除孤儿、把 `msgId` 合并到出站行，保证「一条消息只有一行」，并推 `message_removed`。
- **限流（S4）**：429 → 账号 `rate_limited`，`rate_limited_until = now + retryAfterSeconds`；发送器只挑 `online` 账号的消息，所以等待期内网关收不到 `send`。每个账号严格串行、按 `id` 顺序取队首，到期后按原顺序发出。到期由后台每 250ms 的 CAS 更新恢复（`WHERE status='rate_limited'`，已被改为别的状态则不动）。
- 503 视为未处理，退避后重试（不计入重发次数）。

### 2.3 账号状态机

- 转移表硬编码在共享模块中，前后端共用同一份语义。
- `transition` 接口：校验 → 404 → 按 `expectedFrom→to` 查表（ILLEGAL_TRANSITION）→ `SELECT … FOR UPDATE` 后比较当前状态（CAS_CONFLICT）→ 需要时调网关 `disconnect/connect` → 更新并提交。行锁保证并发时只有一个成功，后到的看到新状态得到 409。
- **进入终态** 统一走 `enterTerminal(tx, accountId, status)`：同一事务内改状态、移除全部群成员关系、取消排队消息（`cancelled / ACCOUNT_TERMINAL`）、对应序列步骤 `skipped`、写 `account_status_changed` 与 `account_terminal` 推送事件；已在终态则静默忽略。来源（发送错误、网关事件、操作员）都调用它。

### 2.4 推送事件与一致性

- 所有业务状态变化在**同一事务**里写入 `ws_events` 表，提交后 `pg_notify` 唤醒分发器，所以推送一定对应已保存的状态。
- `seq` 用 bigserial，写事件前拿事务级 advisory lock（事件写在事务末尾，持锁时间极短），使 `seq` 顺序等于提交顺序，`seq > N` 的补发不会漏。
- WS 认证后可带 `sinceSeq` 补发，前端按 `seq` 去重。

### 2.5 Agent run

- **单 run 约束**：`agent_runs(group_id) WHERE status='running'` 部分唯一索引，多实例也成立。待处理消息存 `agent_pending_triggers`，run 结束的同一事务里若有待处理消息立刻建下一个 run。
- **执行与恢复**：run 由带租约（lease 5s、心跳 1.5s）的工作者执行；所有状态（历史 messages、步数、连续协议错误数、累计活跃时长、待执行工具及其阶段）落库。重启后租约过期被重新认领，用同一 `runId` 继续。累计时长只在持有租约执行时增长，停机时间不计。
- **副作用工具不重放**：`send_message` 在审计通过后与出站消息行、幂等键同一事务写入，之后只等待该消息状态；`kick_user` 调网关前先落「kicking」阶段，恢复时先查网关成员列表，已移除即视为成功。
- **协议错误**：严格 `JSON.parse` 原文 + 形状校验 → `BAD_JSON`；工具名不在 4 个之内 → `UNKNOWN_TOOL`；ajv 校验入参 → `INVALID_INPUT`；`tool_use.id` 在本 run 内出现过 → `DUPLICATE_TOOL_USE_ID`；超时 → `TURN_TIMEOUT`（AbortController，迟到响应丢弃）。前两种追加 assistant 块 + 错误 tool_result；后三种追加 `PROTOCOL_ERROR <code>: …` 文本。合法响应清零连续计数（未知工具/坏入参也计入连续协议错误）。
- **审计**：单次超时 5s（可配），同一工具调用最多 3 次；结论不明确 3 次 → run `blocked / audit_blocked`。
- **幂等**：`agent_idempotency(run_id, key)` → 消息行。重复调用直接返回该消息当前状态，不再审计（S5）。
- **重复调 `get_recent_messages`**：同入参且无新消息时在结果里加 `hint` 提示调用 `finish`；第 3 次起返回 `POLICY_DENIED` 错误；12 步上限兜底。
- **外部状态变化**：每步结束后重读群状态，`unreachable` 或 `agentEnabled=false` → `cancelled`。

### 2.6 定时序列

- 预检纯函数：按步骤顺序累积取值（`vars` 去掉空串 → 每步 `stepVars` 非空值覆盖并记录来源），任意占位符解析不到 → 422，不写任何记录。
- 启动用部分唯一索引保证并发两次恰好一个 201（另一个捕获唯一冲突 → 409）。
- 每次只排期一个步骤：第 1 步 `now + delay`；某步 `sent`（收到 `message_sent` 的时刻）/`skipped` 后在同一事务里排下一步。步骤与出站消息状态联动在消息状态更新的事务内完成。
- 选账号：`admin` 角色取 `role ∈ {creator, admin}` 且 online（优先 admin）；`member` 取 `role = member` 且 online 按 `accountId` 字典序第一个；只有 `rate_limited` 候选时顺延到最早的 `rate_limited_until`；都没有 → `skipped`。
- 重启：启动时只把每个运行中序列「当前待发且已过期」的那一步改到 `now + delaySeconds`。

### 2.7 建群与退群 Job

- Job 状态（阶段、网关群 id、邀请链接、每个成员的进度、promote 调用次数）落库，带租约执行，可在任意阶段恢复。
- 建群：create → invite → 依次 join（`INVITE_NOT_READY` 等 `readyAfterMs` 重试；`INVITE_EXPIRED` 重新申请后重试一次；`ALREADY_MEMBER` 视为成功）→ 等 `member_joined`（10s 超时 → `JOIN_TIMEOUT`）→ promote（只在看到 `member_joined` 之后调用，`NOT_MEMBER_YET` 时等待后再试一次，总调用 ≤ 2）。
- leave-all：先退非群主（失败记错误、继续其余），全部成功才退群主；退群以 `member_left` 为准，5s 未到则以网关成员列表核对；最后用网关成员列表对账。

### 2.8 认证

- access token：JWT（HS256，15 分钟），携带 `sid`；每次请求校验会话未作废 → logout 后同一 token 立即失效。
- refresh token：随机串，仅 HttpOnly cookie 下发，库里存哈希；每次使用轮换；已用过的再出现 → 作废整个会话（该会话所有 refresh/access token 立即失效）。
- 角色：`viewer` 对所有非 GET 业务接口 403。

## 3. 架构

```
apps/
  server/        后端（Fastify + pg + zod + ajv + jose）
    migrations/  SQL 迁移（可重复执行，schema 落后拒绝启动）
    src/
      db/        连接池、事务（带推送事件缓冲）、迁移
      auth/      登录、刷新、登出、鉴权钩子
      realtime/  ws_events 分发、WS 服务
      gateway/   网关客户端、SSE 消费、inbox 处理器
      accounts/  状态机、转移、限流恢复
      messages/  出站发送器、unknown 解析器、时间线查询
      groups/    群查询、建群/退群 job、成员关系
      agent/     Agent 客户端、协议校验、工具、run 执行器、调度器
      sequences/ 占位符解析、序列调度
      media/     媒体下载与清理（C1）
  web/           控制台（React 18 + Vite + React Query）
  mock-gateway/  2.1 网关模拟 + 故障注入控制接口
  mock-agent/    2.2 Agent 模拟 + 脚本化响应控制接口
```

后台工作者（均可多实例并行，靠行锁 / `SKIP LOCKED` / 租约协调）：SSE 消费、inbox 处理、出站发送、unknown 解析、限流恢复、job 执行、agent 调度与执行、序列调度、媒体下载与清理、ws_events 分发。

## 5. API 契约

### 5.1 通用

- 错误：`{ error: { code, message, requestId, ...业务字段 } }`。时间字段 ISO 8601 UTC，无值 `null`。
- 认证：`Authorization: Bearer <accessToken>`；refresh cookie 名 `gp_refresh`（HttpOnly，`Path=/api/auth`，SameSite=Lax）。

### 5.2 端点

题目 2.3 要求的端点全部按原样实现，额外字段与扩展端点如下：

| 端点 | 说明 |
|---|---|
| `POST /api/auth/login` → `{ accessToken, user: { username, role } }` | + Set-Cookie |
| `POST /api/auth/refresh` → `{ accessToken, user }` | 读 cookie，轮换 |
| `POST /api/auth/logout` → `204` | 作废会话、清 cookie |
| `GET /api/auth/me` → `{ username, role }` | |
| `GET /api/accounts` 每项额外 `allowedTransitions: string[]` | 当前状态可转去的状态 |
| `GET /api/groups[/:id]` 额外 `externalMembers: [{ platformUserId }]`、`createdAt` | |
| `GET /api/groups/:id/messages` 每项额外 `id`（行 id，稳定）、`senderAccountId`、`mediaUrl`、`localFilePath`、`source` | |

### 5.3 WebSocket

客户端：`{ type: 'auth', accessToken, sinceSeq? }` → 服务端 `{ type: 'auth', success: true, latestSeq }`（失败 `success: false` 后关闭）。事件帧 `{ seq, type, payload }`：

| type | payload |
|---|---|
| `account_status_changed` | `{ accountId, from, to, account }`（`account` 为完整账号 DTO） |
| `account_terminal` | `{ accountId, status }` |
| `inconsistency` | `{ kind, ref, message }` |
| `message` | `{ groupId, msgId, isOwn, id, clientMsgId, item }`（`item` 为时间线行，状态每次变化都推） |
| `message_removed` | `{ groupId, id }`（孤儿回流行被合并时） |
| `agent_run` | `{ runId, groupId, status, endReason }` |
| `agent_step` | `{ runId, groupId, stepNo }` |
| `sequence_run` | `{ runId, groupId, status, currentStepIndex }` |
| `group_updated` | `{ groupId }` |
| `job` | `{ jobId, type, status, groupId }` |

## 8. 取舍与已知限制

- 网关建群接口没有幂等键：崩溃恰好发生在「网关已建群、本地未落库」之间会多出一个网关群，属于外部约束下无法完全消除的窗口，已把它压缩到一次 HTTP 往返。
- 单进程内用 `pg_notify` + 短轮询唤醒工作者，多实例部署时其它实例靠轮询兜底（≤ 500ms 级延迟）。
